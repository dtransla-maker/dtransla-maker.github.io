In short

What does IEC 62304 software quality assurance cover?

It covers the software lifecycle records IEC 62304 asks for, from the software development plan and Software Requirements Specification (SRS) to architecture, detailed design, and traceability from requirements to risk controls to tests, and the testing that produces the evidence.

MedDev Solutions develops and tests SaMD and embedded firmware with your team and writes those records as the code changes, designed to support compliance with IEC 62304:2006/AMD1:2015.

The handoff

The handoffRequirement change to release

Records written later
  • Development ships a feature. QA tests it.
  • Someone outside the sprint writes the Software Requirements Specification (SRS) and test documentation later.
  • By submission, your IEC 62304 records and your code can describe different versions.
Records written with the code

Mapping the handoff…

  • Requirements enter your backlog with an ID. Tests trace to those IDs.
  • When a requirement changes, the SRS, the tests, and the risk file change in the same sprint.
  • The aim: at release, the records already match the build.

What we deliver

What do we deliver: the software, or the records?

Your device needs working, tested software. Your submission needs the IEC 62304 records for that same software. One team handles both, including embedded firmware.

Development and testing

Code, tests, and quality work done alongside your developers.

  • Software as a Medical Device (SaMD) and digital health software development
  • Embedded firmware, developed and tested as embedded software
  • Senior SQA: low-level QA and testing
  • Verification and validation (V&V) of medical device software
  • Secure Software Development Lifecycle (SSDLC) built into the work

The IEC 62304 documentation set

The software records your Design History File needs, written as the code changes. Designed to support compliance with IEC 62304:2006/AMD1:2015.

  • Software development plan
  • Software Requirements Specification (SRS)
  • Software architecture and detailed design
  • Management of software of unknown provenance (SOUP) and off-the-shelf (OTS) software
  • Traceability from requirements to risk controls to tests
  • Software risk analysis inside your ISO 14971 process

How an engagement runs

How does an engagement run?

In five phases, from records gap review to sustaining engineering. How long each phase takes depends on your codebase and your current records. We agree the scope of each phase together before work starts.

  1. 01

    Assess

    We compare your code, tests, and IEC 62304 records, and list where they disagree, starting with what your submission needs first.

  2. 02

    Plan

    Your software lifecycle process and documentation set, structured to IEC 62304 and fitted to how your team already works.

  3. 03

    Build and test

    Development and low-level testing alongside your developers, with records written as the code changes.

  4. 04

    Verify and validate

    V&V of your medical device software, with each result traced to a requirement and a risk.

  5. 05

    Sustain

    Sustaining engineering after release, with records kept current for every change.
